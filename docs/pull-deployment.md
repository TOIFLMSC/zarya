# Автоматическое обновление Зари на VPS

После однократной установки таймер проверяет актуальный коммит `main` через 90 секунд
после загрузки и примерно каждые две минуты после завершения предыдущей проверки.
Зелёный запуск на PR разрешает ревью. Разрешение на доставку даёт успешный запуск
`ci.yml` на **push в main** для того же SHA. Если два merge следуют подряд,
сервер догоняет текущую проверенную вершину. Все промежуточные SQL-миграции входят
в последний wheel. Остановленная оператором Заря остаётся остановленной при обычном опросе.

## Подключение существующего сервера

Требуются Ubuntu 24.04, systemd с polkit, Python 3.12 с venv, FFmpeg, исходящий
HTTPS к GitHub, хранилищу артефактов и PyPI. Bootstrap рассчитан на существующую
`zarya.service` пользователя `zarya-svc` с кодом в `/opt/zarya` и данными в
`/var/lib/zarya`. Перед первым подключением проверьте внешнюю резервную копию,
свободное место, разрешённый репозиторий в unit и правила ревью ветки.

1. После merge дождитесь успешной сборки именно `main`. Из проверенного checkout
   возьмите каталог `deploy/`. Секреты и рабочая SQLite в комплект не входят.
2. Выдайте fine-grained GitHub token только для репозитория, с правами **Contents read**
   (вершина ветки) и **Actions read** (артефакт). В менеджере секретов либо на VPS
   создайте `/etc/zarya-cd/github-token` с владельцем root, режимом 0600, каталогом
   0700. systemd передаёт файл установщику через `LoadCredential`.
3. Подготовьте публичный ключ age и подключение к обычному Яндекс Диску по
   [руководству резервирования](disk-backup.md). При обновлении предыдущего
   установщика остановите таймеры, дождитесь завершения oneshot и фазы `idle`.
   Выполните команды на VPS. Первая устанавливает проверенные локальные скрипты,
   drop-in исходного сервиса, polkit-правило только для start/stop этого unit,
   oneshot и таймер. Работающий бот продолжает обслуживать сообщения до первого деплоя.
   Для обновления самого контроллера повторите установку из проверенного checkout.
   Автодеплой приложения обновляет wheel и Web UI, а файлы контроллера в
   `/usr/local/lib/zarya-cd` обслуживаются установщиком.

   ```sh
   sudo sh deploy/install.sh
   sudo systemctl start zarya-backup.service
   # После скачивания, расшифровки и проверки первой копии на ПК:
   sudo systemctl enable --now zarya-cd.timer zarya-backup.timer
   systemctl list-timers zarya-cd.timer zarya-backup.timer
   sudo journalctl -u zarya-cd.service -n 60
   ```

Установщик работает под `zarya-svc`. Код контроллера и units принадлежат root;
их изменения устанавливаются отдельно при изменении протокола CD. Управляемый
процесс сохраняет имя `zarya.service`, поэтому существующая карточка process_ground
и локальный туннель ведут к прежней службе. Для приостановки следующей проверки
используйте `systemctl disable --now zarya-cd.timer`; уже начатый oneshot завершает работу.

## Что происходит при обновлении

1. Контроллер берёт `deploy.lock`, читает устойчивый журнал
   `/var/lib/zarya-cd/state.json` и сначала завершает прерванную операцию.
   Уже установленный SHA или версия, отклонённая после отката, пропускаются.
2. По текущему SHA, имени workflow, репозиторию, ветке и событию выбирается последний
   запуск. Контроллер принимает один неистёкший артефакт `zarya-<SHA>` именно этого
   запуска, сверяет SHA-256 архива с GitHub, каждый файл с манифестом и `REVISION`.
   Временное отсутствие CI или сети оставляет работающую версию онлайн.
3. В отдельном каталоге `/var/lib/zarya-cd/releases/` устанавливаются хешированные
   бинарные зависимости, wheel и собранный UI. Выполняются `pip check` и пробный
   import. Повторно проверяются вершина ветки, свободное место и активность службы.
   Если видны выполняющиеся задания, начатые платные вызовы или отправка из outbox,
   контроллер ждёт следующего опроса. Между проверкой и остановкой возможен новый
   запрос; для него действуют обычные правила долговечной очереди и неизвестного результата.
4. До остановки в журнал записывается фаза `stopping`. Launcher блокирует обычный
   старт, включая запуск после reboot, пока выбирается согласованная пара кода и данных.
   После остановки старый Python создаёт и проверяет штатный offline backup SQLite и
   связанных фото/медиа в `runs/<операция>/backup`. Снимок шифруется и проверяется
   на Яндекс Диске до переключения. При ошибке выгрузки возвращается прежняя служба.
   Повтор перехода возможен через час. Ключи, vault и внешняя
   конфигурация хранятся отдельно и требуют собственного внешнего резервирования.
5. Новый Python под instance lock применяет штатные SQL-миграции к отдельной копии
   через `Database.open`. Telegram и workers на этом шаге выключены. Проверяются
   все версии миграций, `integrity_check`, внешние ключи, контрольные суммы связанных
   файлов и значения **всех прежних строк и колонок** с учётом повторов. Это покрывает
   в том числе разрешения, память, историю, offset и outbox. Для намеренного удаления
   или преобразования старых данных сначала нужен проверенный валидатор этой миграции.
6. В фазе `switching` SQLite Backup API транзакционно переносит проверенное
   содержимое в существующий рабочий файл. Так SQLite сама учитывает WAL и блокировки.
   Права рабочего файла и расположение медиа сохраняются. После успешной записи
   контроллер публикует фазу `admitted` и указатель релиза одним atomic replace
   с fsync. Только после этого launcher допускает старт нового процесса.
7. Контроллер запускает `zarya.service`, сверяет SHA в окружении MainPID и ждёт
   ответа `ok` от `/healthz`. В приложении этот endpoint проверяет БД и состояние
   Telegram runtime. Успех фиксируется в журнале. Тест доставки сообщения в настоящий
   чат остаётся отдельной проверкой.

## Сбой и восстановление

| Момент сбоя | Действие |
| --- | --- |
| Скачивание или сборка окружения | На рабочем сервисе изменений нет. Следующий опрос повторяет проверку. |
| Остановка, backup или подготовка копии | Контроллер снова запускает прежнюю версию с прежней БД. Для отклонённого SHA повторная остановка отключена. |
| Перенос в рабочую БД, включая прерывание контроллера | Во время следующего опроса контроллер удерживает сервис, старым Python проверяет backup, возвращает его через SQLite Backup API, допускает прежний код и проверяет здоровье. |
| После `admitted`, в том числе до успевшей выполниться команды start | Контроллер считает новые записи и внешние эффекты возможными. При провале проверки переводит службу в `blocked`, останавливает её и сохраняет текущие данные. |

При `blocked` посмотрите оба журнала и состояние очередей, сохраните свежую
копию и устраните причину. Для повторного запуска уже выбранной версии с текущей
БД после исправления окружения предусмотрена отдельная операторская команда.

```sh
sudo journalctl -u zarya.service -u zarya-cd.service -n 120
sudo cat /var/lib/zarya-cd/state.json
sudo -u zarya-svc /usr/bin/python3 /usr/local/lib/zarya-cd/deployer.py resume-current
```

Backup, сделанный до допуска, может не содержать новых согласий, сообщений, списаний
и отметок отправки. Если требуется замена самой версии после допуска, остановите
таймер, сохраните текущее состояние и согласуйте исправляющую версию/миграцию.
При заполнении диска проверка свободного места блокирует следующий деплой.
После успешного обновления на VPS остаются текущее и предыдущее рабочие окружения
и предрелизный снимок последнего успешного обновления в `runs/`. На ближайшем
опросе работающей службы в фазе `idle` контроллер удаляет лишние окружения и
снимок предыдущего успешного обновления. Прерванная очистка продолжается при
следующем опросе. Ошибка новой версии сохраняет последний успешный снимок.
Материалы неудачной миграции остаются для разбора. Старые снимки, для которых
журнал состояния уже потерял связь с успешной операцией, требуют ручной сверки
с журналом деплоя и подтверждённой внешней копией. Если после обновления старого
контроллера предыдущую рабочую версию определить невозможно, очистка окружений
ждёт первого успешного обновления. Сроки хранения внешних копий описаны в
[руководстве резервирования](disk-backup.md).

## Как повторить проверку на копии

Следующая команда использует штатный снимок с `manifest.json` и отдельный существующий
каталог временных файлов. Она проверяет комплект, применяет миграции, выполняет
переключение и возврат в карантинной временной базе и сравнивает полный логический
дамп с исходным. В журнал попадают только версии схемы и число файлов.

```sh
uv run --locked python deploy/rehearse.py /path/to/verified-backup /path/to/private-tmp
```

## Перенос схемы на другой проект

Клиент `pull_release.py` принимает репозиторий, ветку, имя CI workflow и префикс
артефакта. Для другого сервиса переиспользуйте его вместе с контрактом
`REVISION` и `SHA256SUMS`. Задайте свой unit, пользователя, пути, команду
установки и проверку готовности. Для PostgreSQL, Redis или внешнего хранилища
понадобятся собственные команды снимка, миграции и сверки. Для сервиса без
изменяемых данных переключение можно упростить до замены версии процесса.

Docker совместим с pull-деплоем: CI может публиковать OCI-образ, а сервер —
забирать его по digest. Образ удобен для фиксации системных библиотек или
развёртывания нескольких сервисов через Compose. У Зари уже есть systemd,
FFmpeg, изолированный Python и подключение к process_ground. При переходе на
контейнер SQLite и медиа всё равно требуют отдельного постоянного тома, backup,
миграции и той же границы отката после начала обработки событий.
