# Архитектура

FastAPI/Uvicorn обслуживает авторизованный UI и один supervised lifespan.
aiogram получает Telegram updates; SQLite WAL хранит inbox, jobs, outbox,
смещения получения, версии настроек, доступы, память и учёт запросов к моделям.
Транзакции сериализованы; задача asyncio не заменяет долговечную очередь.

Маршруты разделены: DialogueEngine формирует ответ, PhotoEngine анализирует
фото, MediaEngine готовит речь/кадры через FFmpeg и модель, AvatarEngine работает
с выбранным профилем, MemoryEngine извлекает факты/сводки, ResearchEngine получает
публичные материалы. Неизменяемый PromptBundle выбирается через TelegramStore
по SQL-выпуску настроек, закреплённому за операцией.
Один запуск ResearchEngine может записать два платных вызова. Поиск
первоисточника и небольшое исследование резервируют часть лимита для одной
проверки существенного пробела. Бюджет выходных токенов, включая рассуждения,
составляет до 12 000 для первого поиска и до 6 000 для дополнительной проверки.
Её запрос состоит из фиксированных инструкций,
причины и публичных адресов без query-параметров. Первый результат сохраняется
до второго вызова и остаётся доступным при его сбое или прерывании.
Закрытые ссылки и приглашения Telegram во второй вызов не попадают. Профиль
исследования определяется по словам текущего собеседника без блоков цитат.
Неопределённый вызов автоматически не повторяется. Для точного документа
и официального раздела результат связывается с подтверждённым тезисом и
прочитанной страницей. Вид источника оценивается моделью по содержанию.
В личном чате прямо следующий за вопросом о посте или новости пересланный пост может
закрыть его двухсекундное ожидание. Задание привязывается к текущим ревизиям
обоих событий. Правка вопроса до начала генерации ответа сохраняет срок
ожидания или привязку к уже полученному посту. Уточнения к отправленному
ответу используют тот же пост и его ссылки, пока доступны исходные ревизии
поста и всех выбранных элементов альбома. После правки вопроса локальная
копия отправленного ответа очищается. Новый реплай может восстановить
проверенную привязку к посту. Когда вопрос касается написанной цитаты, поиск
проверяет текст поста до анализа вложений. Итоговый диалог получает результаты
поиска и доступные результаты разбора вложений.
При неизвестном источнике удаляется весь ссылающийся на него тезис. Если
сохранились подтверждённые тезисы, приложение заменяет сводку фиксированным
сообщением о частичном результате и не повторяет поиск из-за этого сбоя.
Официальный OpenAI adapter обслуживает Responses и ASR; модели и глубина выбираются
по маршрутам. Реальные секреты приходят только из локальной конфигурации.

Персональный недавний контекст имеет область `(bot_id, chat_id, grant, user_id)`.
Проекция `participant_messages` хранит только привязки к актуальным разрешённым
событиям, автора и исходный возраст. Окно по умолчанию 20 человеческих сообщений,
включая текущий вопрос; ответы бота не занимают квоту. Активность соседей не
вытесняет это окно. Для ответа выбираются текущий человек и участники проверенной
цепочки реплаев; пересланный текст сохраняет чужое авторство. Старые обрезки
500/40/22000 в этом подборе не используются. Персональная саммаризация заменяет
готовыми блоками часть окна; точные детали и свежий хвост остаются оригиналами.
Перед генерацией проверяется вместимость окончательного запроса в модель;
выбранное окно и обязательные материалы не сокращаются ради лимита.

Связанные ответы — фактически отправленные части `outbox`, а не полный ответ
модели. `context_run_edges` связывает их со снимком нового запроса. Проверка
предков выполняется пакетным обходом DAG без ограничения длины разговора старой
глубиной доказательств памяти. Изменение/удаление источников очищает производные
снимки, запросы и ответы по этим связям. Проверки повторяются до API, при
сохранении, replay и доставке; диагностика окна не разрешает чтение исходников.

Память групп общая для их топиков; разные группы разделены.
Состояние длинной задачи привязано к исходной реплике и одному топику.
Фоновая сводка хранит проверенные фрагменты цели, условий и решений.
См. [состояние длинной задачи](task-state.md).
Личные разговоры изолированы. Перенос личных сведений требует согласия участника;
владелец панели может исправить запись, но не выдать такое согласие за него.
Контекст хранится до 90 дней, факты — до удаления с переоценкой. Зависимости
проверяются при извлечении, генерации, replay и доставке. Отзыв/удаление источника
не должен оставлять его данные в производных ответах.

Правка сообщения сохраняет проверенные, полностью отправленные ответы, чей снимок
контекста сформирован до первого получения редактируемой версии. Порядок определяется
по идентификаторам событий в той же транзакции, а не по часам. Старые снимки без этой
метки, зависимые ответы и случаи переноса сведений между чатами очищаются консервативно.
Удаление памяти, отзыв согласия и срок хранения не используют это исключение.
Текст уже очищенного ответа не восстанавливается из Telegram-цитаты.
Сохранение истории не разрешает replay со старой версией памяти: он по-прежнему
может быть отклонён после изменения memory_epoch.

Цепочки реплаев связываются с выбранным исходным постом и отправленными сообщениями
бота. Они не подменяются последним фото чата.

Смысл запроса, необходимость проверки и манеру ответа поручаем модели. Для
изменения этих решений уточняем промпты и передаём нужный контекст. Код отвечает
за проверяемые границы: полномочия, происхождение данных, типы ссылок, применение
решений модели, бюджеты и устойчивость очереди. Правила по формулировкам добавляем
только там, где границу нельзя обеспечить решением модели.

Для вопроса о выбранном посте короткий вызов без веб-инструментов получает
отдельно слова собеседника, материал поста и результат чтения доступных ссылок.
Инструкция `POST_INTENT_PROMPT` задаёт выбор между ответом по материалу и
проверкой. Для содержательных политических и исторических утверждений и просьб о
проверке модель может разрешить поиск и сформулировать публичный вопрос. При
сбое выбора Заря отвечает по доступному материалу. Фаза учитывается как
`research_intent`; повторный запуск платного решения ограничен журналом.
После решения в веб-поиск передаются публичный вопрос и допустимые очищенные
адреса источников. Текст прочитанных страниц остаётся в контексте диалога.
Внешний поиск в других маршрутах получает вопрос и
выбранный материал в пределах лимитов, без личной памяти и окна недавней
переписки. Первый запрос передаёт подтверждённые загрузчиком HTTP(S)-адреса
без параметров запроса. Для YouTube используется канонический адрес по video ID.
Повторная проверка свежей новости может также передать публичные адреса из
предыдущей проверки, привязанной к исходному ответу. Старая задача без метки
происхождения может завершиться без внешнего поиска при обновлении. Вопрос и выбранный текст
могут содержать личные сведения, если пользователь включил их в запрос.
Содержимое страниц, медиа, памяти и сообщений считается недоверенными
данными. Обычный диалог не получает инструментов. Для автоматического
оспаривания факта требуется свидетельство от самого участника.

Неопределённый результат платного вызова автоматически не повторяется.
Повторная доставка ограничена состоянием outbox и ошибкой транспорта. Локальный
журнал хранит запросы, ответы, причины решений и usage; скрытые рассуждения модели
не являются доступным пользовательским журналом.

Сборка UI раздаётся Python-сервером; отдельный Node.js backend не нужен.
Миграции: src/zarya/migrations, зависимости: uv.lock и web/pnpm-lock.yaml.

GraphRepository даёт ограниченный read-only граф текущей памяти. ObsidianBridge
работает в общем lifespan и экспортирует его в управляемую папку. SQL остаётся
каноническим: Markdown-правка создаёт предложение, а владелец применяет его через
одну версионированную команду памяти. Журнал обеспечивает дедупликацию и возврат
текста; источники, согласия и старые задания не восстанавливаются. Отзыв/удаление
очищают зависимые тексты и ставят заметки в очередь очистки. Промпты и CodeGraph
в этот мост не входят.

ConfigurationBridge отдельно экспортирует полный набор настроек и фрагментов
инструкций в связанную папку Obsidian. Markdown служит редактором и графовым
представлением, а SQL — рабочим источником. Две стабильные проверки создают
черновик; явное решение владельца атомарно активирует настройки и промпты.
Версия и точные файлы проверяются до фиксации. Выпуски неизменяемы, откат создаёт
новый выпуск без возобновления отменённых заданий. Первоначальный prompts.json
после импорта не является живой конфигурацией. Конфигурация и использование —
в configuration.md и operations.md.

CodeGraph — отдельный CLI разработки на стандартной библиотеке Python.
Он строит структурный индекс текущих исходников, тестов и ссылок в публичной
документации, проверяя набор файлов и хеши до и после разбора. CLI не запускает
приложение, не открывает SQLite и не вызывает модели. Локальный индекс хранится
в data/codegraph/index.json, а карта Obsidian экспортируется в отдельную папку.
Связи импортов помогают выбрать кандидатов тестов; динамические вызовы остаются
неопределёнными. Подробности и команды — в [codegraph.md](codegraph.md).

Персональная саммаризация (миграция 023) — дополнительный вид durable работы в
существующем MemoryEngine/supervisor. Из востребованного разрешённого окна выделяются
непересекающиеся блоки по пять человеческих оригиналов с bot/chat/grant/user scope.
Очередь ограничена 32 queued/started блоками; запуск не обрабатывает массово 90-дневную
историю. Факты и сводки выполняются по очереди. Просмотр UI, initiative и replay не
создают платных блоков. Ответы Зари не входят в сводки и сохраняются точными sent parts.

Текущий вопрос, последние две реплики истории, точные выбранные реплаи, числа,
ссылки, вложения, пересылки и отрицания остаются оригиналами. Готовый блок заменяет
только доступный целиком участок выбранного окна и только если уменьшает вход.
Частичный блок на границе, очередь и ошибки используют raw fallback. Сводки никогда
не составляются из прежних сводок. Смысловой пересказ может терять нюансы: источники
доступны для проверки и не превращаются в подтверждённые факты профиля.

Все исходные revision/retention refs остаются в snapshot, дополнительно проверяются
ID и хеш текста использованного блока. Проверки выполняются до вызова, фиксации,
доставки и replay, включая DAG предшествующих ответов. Edit/forget/revoke/media purge
и истечение источников очищают сводки, запросы и зависимые ответы с сохранением
provider ledger. Начатая работа после рестарта становится unknown. Ни unknown, ни
ошибка, ни смена модели/предела/инструкции не запускают повторную платную операцию
по тем же оригинальным revisions. Связь model_calls с блоком уникальна.

Полная сборка контекста включает инструкции, персональные оригиналы/готовые сводки,
связанные sent ответы, реплаи, факты, результаты поиска, формат поведения и реальные
прикреплённые изображения. `context_budget` проверяет именно окончательный payload,
а не более объёмный диагностический snapshot. Уплотняются только JSON-пробелы;
серверное усечение отключено (`truncation=disabled`).

Для пилотной форумной группы адресованный запрос получает
`topic_context` из принятых реплик людей в той же теме. Сообщения форума
без ID темы образуют отдельное окно общего топика. Берутся до восьми
новейших текстовых сообщений за сутки и до 2500 символов суммарно. Модель
получает их от старых к новым вместе с автором, ID сообщения, ID актуальной
ревизии и исходным временем. Персональное окно в пилоте берёт ту же тему и
явную цепочку ответов. Уже поданные оригиналы и выбранные материалы не
повторяются в хронологии. Хронология не участвует в подборе долговременной
памяти и интернет-поиске. Выбранный источник реплая проходит обычную проверку
доступа и ревизий. Автоматическая ссылка Telegram на служебное сообщение
создания топика не продолжает цепочку реплаев. Источники хронологии включаются
в ту же проверку перед вызовом модели, доставкой и повтором. Правка или локальное
стирание источника делает старый снимок недействительным. Telegram в используемом режиме не
присылает уведомления об удалении обычных сообщений.

Явная короткая просьба дословно процитировать реплику участника копирует
сохранённый текст или подпись источника через обычный outbox. Не запрашиваются
модель и поиск. Цитата привязана к текущей ревизии исходного сообщения и
реплая с просьбой. Перед доставкой проверяются доступ и обе ревизии.
Если текст недоступен или не помещается в одно сообщение, Заря сообщает об
этом. Для дословного текста со ссылкой нужна явная просьба «со ссылкой».

В разрешённой группе с включёнными сериями первая адресованная локальная текстовая реплика открывает
серию. Тот же автор может присоединять ещё до четырёх реплик в том же чате
и топике. Приём закрывается после двух секунд тишины, максимум через три секунды
с начала серии. Чтобы не склеить отложенные обновления, учитывается также
время отправки Telegram. SQLite хранит дедлайн, порядок и актуальные ревизии. Правка
до начала обработки заменяет свою ревизию. После начала обработки правка
аннулирует устаревший запрос и ожидающую доставку без повторного вызова.
Один структурированный ответ покрывает все ID и привязывает части к выбранным
репликам. При реплае на ответ используются источники именно этой части.
Отсутствующий или неизвестный ID вызывает сообщение об ошибке
адресации. Поиск, явные реплаи, медиа, запросы аватаров и дословные цитаты
остаются на обычном пути. В серии из нескольких реплик используется только
текстовый ответ. Правила реакции и настроения продолжают работать для
одиночных обращений.

Для обычного входа с большим запасом используется локальная инженерная оценка
UTF-8/framing/изображений. Это не точный токенизатор и не доказанная верхняя граница.
Большой либо неизвестный формат требует Responses input-token count. Высокая оценка
сама по себе не доказывает переполнение: решение уточняет API. Профили обоих
поддерживаемых моделей — 1 050 000 токенов контекста и 128 000 максимального выхода,
проверены по [официальной документации Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)
и [Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol) 13 октября 2026.
Выделяется резерв `max_output_tokens` (уже включает рассуждения) и служебные 8192 токена.

Подсчёт использует тот же явный вход, изображения и формат ответа, без provider
conversation/previous_response_id и без исполнения поиска. После него заново
проверяются доступ, revisions/retention, память и источник запроса. Проверка работает
и для нового платного replay; сохранённый replay не вызывает API. При подтверждённом
переполнении или невозможности проверить большой вход генерации нет. Адресованный
живой вопрос получает короткое служебное сообщение через обычный durable outbox;
инициатива, shadow и replay его в Telegram не отправляют.

Миграция 024 выделяет отдельный ledger для count, без сохранения payload/base64
и выдуманного usage. Тариф этого endpoint не подтверждён; стоимость неизвестна,
а не нулевая. До durable границы генерации основная запись — `preflight`, её
подтверждённая стоимость генерации 0 и latency отсутствует. После границы возможный
платный вызов имеет прежнюю семантику unknown при обрыве. Рестарт/отмена не повторяют
ни подсчёт, ни генерацию автоматически. Подробности состава, оценка и результат
подсчёта доступны в «Диалогах»; они не дублируют тексты инструкций и материалов.

Персональные блоки входят в read-only граф отдельными узлами `participant_summary`
и `participant_source`. Первый использует block ID, второй — event ID; пространство
ID отличается от прежних `source`/memory_sources. Проекция `participant_graph`
проверяет completed result, пять оригиналов с точными revisions и membership,
автора, актуальный bot/chat/grant, возраст исходников и media refs. Неполный или
устаревший блок исключается целиком. Sources читаются по manifest из events,
не из ограниченного пула извлечения фактов. Связи сохраняют принадлежность чату,
отправителя и происхождение, не превращая пересказ в доказательство утверждений.

GraphRepository ограничивает новый срез 50 кандидатами сводок и 250 репликами,
с отдельным покрытием; общие пределы текста и связей сохраняются. ObsidianBridge
проверяет lifecycle этих типов независимо от ограниченного снимка и повторяет
проверку текущего content hash непосредственно перед записью под store.gate.
